2026-09-13 — Time scales repointed to forTime; forapollo_time.f90 retired

changeOne leap-second table, and it is forTime's

forapollo_time.f90 duplicated forTime's scales: 15 fa_time_* routines and three copies of the 28-entry leap-second table. It is deleted. The Zig dead chain that led into it is deleted with it: 15 externs in fortran.zig, timeGmst/timeCalToJd/timeUtcToTai in dispatch.zig, and the Makefile and Stage 2 object-gate entries. The three public exports keep their names and signatures, and each now calls forTime's C ABI directly:

  • fapo_time_gmst → ftim_gmst
  • fapo_time_cal_to_jd → ftim_jd_from_civil_cal, calendar 0 (proleptic Gregorian)
  • fapo_time_utc_to_tai → ftim_mjd_from_jd, ftim_utc_to_tai, ftim_jd_from_mjd

The ftim_* externs sit at the call site in exports.zig. No forTime module is imported, no forTime source is compiled, and there is no wrapper.

Wiring: forTime's prebuilt binary, by path

The old -lfortime by-name lookup searched prebuilt/<t>/lib and zig-out. Neither is where forTime delivers, and nothing called forTime anyway. Both the lookup and the search paths are gone. zig build shared and zig build test now link ../forTime/prebuilt/<short>/libfortime.a by path (-Dfortime-archive= overrides it). A missing archive fails those steps with an explicit message. The static delivery never links forTime and is not gated on it.

Consumers: link libfortime.a beside libforapollo.a. The archive's public name set is unchanged (66 fapo_*, compared in both directions). Its undefined set gains exactly ftim_gmst, ftim_jd_from_civil_cal, ftim_mjd_from_jd, ftim_jd_from_mjd and ftim_utc_to_tai. ftim_jd_from_civil_cal first shipped in forTime 99160b5.
No local may escape to the extern. The first cut passed &tai_sec to ftim_utc_to_tai. In ReleaseSafe that plants a stack-protector canary: the archive gained U __stack_chk_fail, U __stack_chk_guard and a global .refptr.__stack_chk_guard, which every consumer, MSVC included, would have had to resolve. The export now passes the caller's own out-pointer.

Behaviour, measured

Old and new exports were called with identical inputs and every result compared. The inputs were dense: every leap-second boundary ±1 day, the 1582 reform, JD 0 through 2150, and valid, invalid and negative-year civil dates. That gave 8,086 public calls, plus 38,785 calls to the 12 unexported routines against their forTime equivalents. Each difference was then assigned to a mechanism, by reimplementing the old kernel and forTime independently and requiring both reimplementations to reproduce the measured values. None was left unexplained.

  • fapo_time_utc_to_tai: from 1972 on, identical or within 1 ULP of the JD (≤ 40 µs). Before 1972-01-01 the result moves +10 s, because forTime applies TAI−UTC = 10 s there and the old table applied 0 s.
  • fapo_time_gmst: same IAU 1982 model, restated in degrees with rounded coefficients. The result moves by ≤ 2.4e-9 rad (34 µs) over 1900–2100, and by at most 1.8e-7 rad at JD 0. A non-finite JD now reports info = 3.
  • fapo_time_cal_to_jd: 1,357 valid dates are bit-identical. 80 negative-year dates are now exact; the old Meeus integer truncation put them up to one day off. 118 impossible inputs now give info = 3 and jd = NaN, where the old kernel returned a rolled-over JD with info = 0.

openforTime defects found (not reachable through forApollo's exports)

  • ftim_tt_to_tdb evaluates its Fairhead–Bretagnon series with t in Julian centuries. The series' frequencies are per millennium, so the result is off by up to 3.3 ms.
  • ftim_tai_to_utc: for a TAI instant inside an inserted leap second, utc = tai − (d − 1) returns a time 2 s late, and the result does not satisfy its own utc + lookup(utc) == tai check.

2026-08-05 — Stage 1 made external: make shell-out removed, object gate added

fixbuild.zig no longer invokes make

Stage 1 was reached by shelling out to make from build.zig (make lib TARGET=<target>), with 3 steps depending on it. That ordered the build correctly but handed Zig a stage its build graph cannot see.

Why the shell-out is the problem, not just the ordering. Zig's build system is a dependency graph, not a script runner. A Run step declares no inputs, so Zig cannot hash the .f90 sources or the .o outputs — it therefore cannot answer "is Stage 1 stale?" and either re-runs make unconditionally or never. Cross-compilation breaks too, because the make invocation knows nothing about the Zig target.

Stage 1 is now fully external and Stage 2 gates on the objects:

make lib TARGET=<target>   # Stage 1
zig build          # Stage 2

Missing objects are a hard failure

A config-time gate checks every expected Stage 1 object and panics with copy-pasteable instructions when one is absent. Wrapping zero Fortran members yields an archive that links but is missing every kernel — a failure that only surfaces at runtime in the consumer, far from the cause.

The gate is unconditional: the objects are consumed whether Stage 1 just ran or they were committed under -Duse-prebuilt, so either way they must be present.

The gate probes via b.pathFromRoot(), not std.fs.cwd(). build() runs for every package in the graph, but the process cwd is always the root package's directory — so a relative probe inside a library's build.zig looks inside the consumer's tree when that library is built as a dependency. A first cut of this gate used cwd and broke forAI's build via forNet before being caught.
