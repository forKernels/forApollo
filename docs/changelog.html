2026-08-05 — Stage 1 made external: make shell-out removed, object gate added

fixbuild.zig no longer invokes make

Stage 1 was reached by shelling out to make from build.zig (make lib TARGET=<target>), with 3 steps depending on it. That ordered the build correctly but handed Zig a stage its build graph cannot see.

Why the shell-out is the problem, not just the ordering. Zig's build system is a dependency graph, not a script runner. A Run step declares no inputs, so Zig cannot hash the .f90 sources or the .o outputs — it therefore cannot answer "is Stage 1 stale?" and either re-runs make unconditionally or never. Cross-compilation breaks too, because the make invocation knows nothing about the Zig target.

Stage 1 is now fully external and Stage 2 gates on the objects:

make lib TARGET=<target>   # Stage 1
zig build          # Stage 2

Missing objects are a hard failure

A config-time gate checks every expected Stage 1 object and panics with copy-pasteable instructions when one is absent. Wrapping zero Fortran members yields an archive that links but is missing every kernel — a failure that only surfaces at runtime in the consumer, far from the cause.

The gate is unconditional: the objects are consumed whether Stage 1 just ran or they were committed under -Duse-prebuilt, so either way they must be present.

The gate probes via b.pathFromRoot(), not std.fs.cwd(). build() runs for every package in the graph, but the process cwd is always the root package's directory — so a relative probe inside a library's build.zig looks inside the consumer's tree when that library is built as a dependency. A first cut of this gate used cwd and broke forAI's build via forNet before being caught.
